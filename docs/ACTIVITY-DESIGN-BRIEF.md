# 방문·로그인 현황

2026-11-04 · 구현 완료, 운영 DB 적용 대기. 기준: DESIGN-GUIDELINES.md, DESIGN-BRIEF-TEMPLATE.md.

## 목적과 화면

운영자가 현재 누가 활동하고 있고 방문이 얼마나 발생하는지 확인한다.
관리자 메뉴 → `/admin/activity`: 현재 방문 브라우저·활동 로그인 계정·오늘 방문·누적 방문·누적 브라우저·가입 계정,
활동 사용자 표, 최근 로그인 계정 50개, 최근 30일 집계 순서로 표시한다.
기존 색·글꼴·버튼을 사용하고 모바일에서는 카드를 한 열로, 넓은 표는 내부 스크롤로 표시한다.
공개 화면에는 이름·이메일·접속 현황을 노출하지 않는다.
요청자가 지정한 최초 관리자: `jinha@dspubs.org`. 실제 Google 계정 및 이메일 확인 상태 확인 후 UUID에 역할을 부여한다.

## 지표 정의

- 현재: 최근 5분 내 화면이 열린 상태에서 heartbeat가 도착한 브라우저. 1분마다 전송, 숨겨진 탭에서는 중단.
- 로그인 사용자: 위 브라우저와 연결된 검증된 Auth 계정의 중복 없는 목록. 로그인 세션 전체의 유효 여부를 뜻하지 않음.
- 방문: 동일 쿠키로 30분 미만 간격의 활동을 한 번으로 집계. 새로고침·여러 탭은 중복 집계하지 않음.
- 누적 브라우저: 집계 시작 이후 서로 다른 임의 쿠키 ID 수. 사람 수가 아니며 쿠키 삭제·다른 기기에서 증가할 수 있음.
- 오늘/일별: 한국시간(Asia/Seoul). 과거 방문을 복원하거나 추정하지 않음.
- 최근 로그인: Auth의 계정별 last_sign_in_at. 새 방문 집계 이전 로그인도 실제 기록이면 표시.

## 저장과 권한

브라우저 임의 UUID는 HttpOnly·Secure·SameSite=Lax 쿠키로 보관하며 최대 1년.
DB는 UUID·Auth UUID·최초/최근 시각과 날짜별/전체 집계만 저장한다. 검색어·URL·IP·이메일 사본은 저장하지 않는다.
계정 이름·이메일은 관리자 RPC가 Auth에서 조회한다. `about#data-policy`에 안내한다.
클라이언트 제공 사용자 ID·시간·카운터는 받지 않는다. PostgREST가 검증한 JWT의 auth.uid()만 사용한다.
집계 RPC는 익명 방문 기록에 필요하므로 anon에도 실행을 허용하지만 원시 테이블은 RLS와 권한 회수로 직접 접근 금지.
쿠키 UUID는 추측하기 어렵지만 방문 기록 RPC 자체는 공개이므로 자동화로 수치를 부풀리는 공격을 완전히 방지하지 못한다.
따라서 결제·보안 감사·정확한 인원 통계에 사용하지 않는다.
서버 페이지/API의 관리자 확인에 더해 DB 조회 함수도 role_assignments를 검사한다.
오류 시 0이나 예시 값을 채우지 않고 오류를 표시한다. 이전 값이 있다면 마지막 확인 값임을 표시한다.

Hub는 공통 layout에서, DEMO는 공통 관문이 HTML에 같은 자체 스크립트를 붙여 집계한다.
다운로드·API 응답·NAS 원본은 바꾸지 않는다. tools.osh.ai.kr 직접 접속 및 외부 연결 도구는 이 사이트 집계에서 제외한다.

## 배포와 검증

DB migration: `supabase/migrations/202611040001_site_activity.sql`. 카탈로그 초안을 통째로 적용하지 않고 필요한 권한 테이블과 방문 집계만 추가한다.
새 환경변수/서비스 키는 웹에 필요 없다. 기존 Supabase URL·publishable key·APP_URL·Google 설정을 사용한다.
DB 관리 연결이 확보되어야 migration 및 최초 관리자 지정이 가능하다.
상태: 로컬 서버에 Storage 키만 확인됨. 운영 DB 변경 및 관리자 지정은 아직 미완료.
운영 REST 조회에서 `role_assignments`·`profiles`가 없는 것을 확인했다.
요청한 관리자 이메일에 일치하는 실제 가입 계정 1개, Google provider 및 이메일 확인 상태를 확인했다.
Auth 마지막 로그인 시각을 현재 접속 상태로 잘못 표시하지 않는다.

DB 관리자가 Supabase SQL Editor에서 순서대로 실행할 파일:
1. `supabase/migrations/202611040001_site_activity.sql`
2. `supabase/operations/20261104_activity_admin.sql`

두 번째 파일은 지정된 이메일과 확인된 Google identity가 정확히 한 계정에 일치할 때만 관리자 역할을 추가한다.
계정·로그인 세션·가짜 API 키는 만들지 않는다. 기존 프로필 권한을 변경하지 않는다.
DB 연결 정보가 제공되면 위 적용 → production 배포 → 관문 코드 반영 및 기존 서비스 재시작 → 실계정 관리자 화면 확인 순서로 마무리한다.
확인되지 않은 DB 작업을 실행됐다고 표시하거나, 실패 응답을 0명으로 채우지 않는다.

확인 항목: 익명/일반 회원 관리자 조회 차단, 프로필 역할 위조 차단, 사용자 ID 주입 차단,
RLS 직접 조회 차단, 여러 탭 중복·30분 경계·5분 만료·한국시간 집계, 로그아웃 후 사용자 연결 해제,
빈/오류 상태, 데스크톱·360px·키보드·다운로드 영향 없음, lint/typecheck/tests/build.

로컬 검증: 웹 단위 테스트 78개(PGlite의 실제 PostgreSQL 실행으로 migration·RLS·역할 부여·집계 경계를 검사),
Python 관문/정적 자산 회귀 테스트 33개 통과. 웹 빌드·typecheck 통과, lint는 기존 안전대 스크립트 경고 1개.
실제 Google 로그인을 흉내 내는 테스트 경로는 만들지 않았다. 관리자 화면 브라우저 검사는
운영 라우트 밖의 명시적 DEMO 컴포넌트로 수행한다. 운영 관리자 로그인·운영 집계 지속성은 DB 적용 후 확인해야 한다.
기존 손실연수 데스크톱/모바일 계산·다운로드 2개 및 관리자 URL 위조 접근 차단 4개 E2E 통과.
